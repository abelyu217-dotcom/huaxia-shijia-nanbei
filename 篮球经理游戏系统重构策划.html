2. 全局架构：去多世界 → 国家化

2.1 架构对比

维度当前（多世界）重构后（国家化）
世界多个 World，每世界 16 队，互相隔离单一全球生态
组织单元World → TeamCountry → League → Team
跨国交易禁止允许（受国籍/联赛规则限制）
国际赛事每世界取前 2 参加各国 L1 前 N 名 + 外卡，32 队
球员池按世界隔离全球统一自由球员池 + 选秀

2.2 国家体系

首批开放 5 个国家，后续可扩展：

3. 联赛系统：国际 32 / 国内 12 + 升降级

3.1 联赛层级

赛事球队数赛制晋级/降级
国内 L112双循环主客场（22 轮）+ 季后赛前 8后 2 降级到 L2
国内 L212双循环（22 轮）+ 季后赛前 8前 2 升级到 L1
国内杯赛24（L1+L2）单败淘汰冠军获国际外卡资格
国际冠军杯328 组小组赛 → 淘汰赛各国 L1 前 2 + 杯赛冠军 + 外卡

3.2 赛程规则

  • 赛季周期：现实时间 1 天 = 游戏内 1 轮（可配置）。
  • 国内联赛：每周二、四、六进行（L1 与 L2 同日不同时）。
  • 国内杯赛：穿插在联赛周中（周三）。
  • 国际冠军杯：国内联赛休赛期进行（赛季末 4 周）。
  • 双线作战：同一球队在国内+国际赛事时，自动排程避免同日冲突。

3.3 升降级规则

  1. L1 常规赛排名后 2 名 → 降入 L2。
  2. L2 季后赛冠军 + 亚军 → 升入 L1。
  3. 升级/降级在下赛季开赛前完成，球队保留球员但联赛身份变更。
  4. 降级触发职员士气下降、球迷不满、预算削减等连锁效果。

3.4 国际冠军杯资格分配（32 队）

5 国 × L1 冠军  = 5 队
5 国 × L1 亚军  = 5 队
5 国 × 杯赛冠军 = 5 队
外卡（按欧战积分排名） = 17 队
─────────────────────────
合计            = 32 队

4. 球队职员系统

4.1 岗位定义

岗位职责对球队的影响
主教练 Head Coach制定战术、轮换、临场指挥战术执行加成、球员士气
助理教练 Asst Coach专项训练（进攻/防守）球员对应属性成长 +10~20%
训练师 Trainer身体训练、体能恢复伤病恢复速度 +20~40%，体能消耗 -10%
队医 Team Doctor伤病诊治、预防伤病发生率 -15~30%，复出时间 -20%
球探 Scout探查球员、选秀评估探查准确率、报告深度
经纪人 Agent球员合同谈判（球队方）谈判成功率、薪资压制
数据分析师 Analyst数据分析、对手研究赛前情报加成

4.2 数据模型（新增 Staff 表）

Staff {
  id              String   PK
  teamId          String?  FK → Team（无=自由职员）
  role            Enum     head_coach|asst_coach|trainer|doctor|scout|agent|analyst
  name            String
  age             Int
  nationality     String
  reputation      Int      0-100（声望，影响可吸引的球员/薪资要求）
  salary          Float    周薪
  contractYears   Int
  specialties     Json     { offense: 80, defense: 70, ... }（擅长领域）
  efficiency      Int      0-100（工作效率，随经验/士气浮动）
  mood            Int      0-100（士气）
  isUserControlled Boolean  是否由玩家 Professional 担任
  professionalId  String?  FK → Professional（若由玩家担任）
  createdAt       DateTime
}

4.3 核心接口

方法路径说明
GET/api/staff职员列表（按岗位/球队筛选）
GET/api/staff/:id职员详情
GET/api/teams/:id/staff某队职员组
POST/api/teams/:id/staff/hire雇佣职员（经理）
POST/api/staff/:id/fire解雇职员（支付违约金）
POST/api/staff/:id/contract续约/调整合同
POST/api/professional/:id/employ玩家职业接受球队雇佣（打通第三身份）

4.4 玩法闭环

  1. 经理查看职员市场，雇佣教练组。
  2. 主教练设定战术偏好，影响比赛模拟加成。
  3. 训练师/队医在后台持续影响球员状态（每轮结算）。
  4. 球探派往目标球员，产出探查报告。
  5. 职员士气影响效率；战绩差 → 士气降 → 效率降 → 恶性循环，经理需及时调整。
  6. 玩家的 Professional 身份可应聘某球队岗位，领取薪资 + 积累声望。

5. 经纪人系统

5.1 定位

经纪人是球员与球队之间的中介。每名球员可有一名经纪人（也可无）。经纪人代表球员谈判合同，抽取佣金。

5.2 数据模型

Agent {
  id              String   PK
  name            String
  reputation      Int      0-100（声望越高，能吸引的球员质量越高）
  commissionRate  Float    0.02~0.10（佣金比例）
  specialty       String?  擅长领域（新秀/巨星/国际球员）
  isUserControlled Boolean
  professionalId  String?  FK → Professional（若由玩家担任）
}

AgentContract {
  id          String PK
  agentId     String FK → Agent
  playerId    String FK → Player
  startYear   Int
  endYear     Int
  commissionRate Float
  status      Enum active|expired|terminated
}

5.3 核心接口

方法路径说明
GET/api/agents经纪人列表
GET/api/players/:id/agent球员当前经纪人
POST/api/agents/:id/sign-player经纪人签约球员（玩家 agent 职业）
POST/api/players/:id/negotiate经纪人代表球员发起合同谈判
POST/api/contracts/:id/negotiate经理与经纪人谈判（经纪人提高/降低要价）

5.4 玩法闭环

  1. 球员生成时，AI 经纪人按声望自动分配（或无经纪人）。
  2. 经理签约球员时，若球员有经纪人，需与经纪人谈判（经纪人会加价）。
  3. 经纪人声望越高，要价越强硬，但球员更愿意签约。
  4. 玩家 Professional(agent) 可主动招揽球员为客户，谈判成功抽取佣金。
  5. 经纪人-球员关系随时间变化，球员可在合同到期后更换经纪人。

6. 第三身份职业玩法闭环

6.1 职业玩法矩阵

职业核心行动收益关联系统

助教选择训练科目，执行训练计划训练加成 + 经验Training, Staff
主帅受雇后设定战术/轮换，临场指挥战绩奖金 + 声望Match, Staff
训练师制定恢复计划，管理球员体能恢复效率 + 经验Player condition, Staff
经纪人招揽球员客户，谈判合同佣金抽成 + 声望Agent, Contract
商人洽谈赞助、周边运营收入分成Team finance
球馆运营票价定价、活动策划、上座率优化球馆收入Arena
记者撰写报道、专访球员稿费 + 影响力Media

工会代表参与劳资谈判球员福利影响CBA

6.2 关键机制：雇佣打通

Professional.employmentStatus 不再是死字段。玩家职业可通过 /api/professional/:id/employ 受雇于某球队的对应 Staff 岗位，实现"身份 → 岗位"打通。受雇后：

  • 领取球队发放的薪资
  • 执行该岗位的日常行动
  • 战绩/绩效影响续约与声望
  • 可主动辞职或被解雇

6.3 职业独立玩法（无需受雇）

部分职业（经纪人、记者、解说员、商人）无需受雇于球队即可开展业务，自由接单获利。

7. 核心球员定义修正

7.1 定义

核心球员 = 球员化身（Avatar），即玩家自创并控制的球员，以及联盟中其他玩家的化身。它是"人"的概念，不是"队内能力最强"的概念。

7.2 实现

  • CorePlayersPage 改为展示全联盟玩家 Avatar 列表。
  • 支持按球队、国籍、位置、是否自己的化身筛选。
  • 展示化身的控制模式（手动/自动）、成长轨迹、当前球队、赛季数据。
  • 原"OVR Top5"改名为"主力阵容"或"关键球员"，与"核心球员"概念分离。

8. 球员化身创建扩充

8.1 创建参数

AvatarCreateParams {
  name: String
  position: PG|SG|SF|PF|C
  playStyle: String            // 打法风格
  height: Int                  // cm（范围按位置校验）
  weight: Int                  // kg
  nationality: String          // 国家代码
  hometown: String?            // 出生地
  personality: String          // 性格类型
  familyBackground: String?    // 家庭背景（可选，不填则随机）
  abilityPoints: {             // 初始能力点分配（预算内自由分配）
    close: Int, midRange: Int, threePoint: Int, drive: Int,
    post: Int, passing: Int, handle: Int, ...
  }
}

8.2 能力点分配规则

  • 初始总预算：300 点（17 项属性，每项初始 30，可自由调配至每项上限 99）。
  • 身高/体重影响身体属性上限（如身高 ≥ 210cm，内线属性上限 +5）。
  • 性格影响精神属性倾向（如"硬汉"类型，clutch/strength 初始 +5）。

8.3 性格类型

9. 普通球员家庭背景随机生成

9.1 生成逻辑

在 world.service.ts 生成球队时，为每名普通球员创建 PlayerFamily 记录：

背景分布（随机）：
  体育世家 athlete_family    15%  →  初始能力 +5，成长 +10%
  普通家庭 regular           50%  →  无加成
  单亲家庭 single_parent     15%  →  性格倾向"硬汉/勤奋"
  海外背景 overseas          10%  →  国籍随机，外语加成
  体校出身 sports_school     10%  →  纪律 +5，基础扎实

9.2 家庭成员生成

PlayerFamily.members: [
  { name, relation: father|mother|sibling|spouse|child, age, occupation? }
]
随机生成 2~4 名成员，姓名按国籍/地区匹配。

9.3 与化身的区别

  • 化身：玩家可手动选择家庭背景（不选则随机）。
  • 普通球员：完全由系统随机生成，玩家不可干预。

12.3 迁移策略

  1. 新建 Country 表，插入 5 个初始国家。
  2. Team 增加 countryId，按现有 worldId 映射到国家（每个 world → 一个 country）。
  3. 球员扩展字段默认值填充（height/weight 按位置生成，nationality 按 country，其余随机）。
  4. 为每名球员创建 PlayerFamily 记录（随机背景）。
  5. 生成 Staff 数据（每队 AI 教练组 4~6 人）。
  6. 生成 Agent 数据并分配给球员。
  7. 验证数据完整性后，删除 World 表。
