1技术选型与理由

选型原则：① 前后端类型共享（TypeScript 同构）——SimInput/Player/Team 等类型前端后端共用，减少接口对接成本；② sim 引擎是纯函数，TypeScript 性能足够（每日批量结算，非实时高频）；③ 生态成熟、招人容易、开发速度快——M0 阶段小团队的务实选择；④ 可独立扩展——sim worker 可水平扩展。

1.2 为什么不是 Go / Rust

Go/Rust 在 sim 性能上更强，但 HWO 的 sim 是每日批量结算（非实时高频），TypeScript 纯函数性能完全足够。选择 TypeScript 全栈的核心收益是前后端类型共享——一个 Player 类型定义在共享包里，前端后端共用，接口对接成本归零。对小团队（M0 阶段）这是最高效的选择。若未来 sim 性能成为瓶颈，sim 引擎可单独用 Go 重写为微服务，不影响整体架构。

2.2 核心设计原则

服务端权威 铁律
所有 sim/结算/经济计算在服务端执行；前端只读结果。比赛结果不可篡改。
纯函数 sim 确定性
sim-engine 是纯函数，输入相同输出相同。可单测、可回放、可灰度调参、可防作弊。
批量结算 性能
非实时对战——每日 10:00 全世界批量 sim。这大幅降低实时性要求，性能压力集中在结算窗口。
分世界分片 扩展
每个世界独立分片，sim 任务按世界分配 worker，DB 按世界分区，避免单点热点。

3.2 sim-engine 模块详细

sim-engine 是核心中的核心——纯函数，零副作用。

// sim-engine 核心接口（共享类型包 @hwo/shared） export interface SimInput { matchup: Matchup; // 主客队 + 战术 + 轮换 players: Player[]; // 双方球员能力快照 tactics: TacticModSet[]; // 战术参数修正 conditions: ConditionState;// 疲劳/状态/化学反应 seed: number; // 确定性 PRNG 种子 config: SimConfig; // 灰度参数（可热更新） } export interface SimOutput { pbp: PbpEvent[]; // 回合级 play-by-play boxScore: BoxScore; // 技术统计 result: MatchResult; // 比分/胜负 rngLog: RngLogEntry[]; // RNG 消耗日志（审计用） } // 纯函数——输入相同则输出相同 export function simulate(input: SimInput): SimOutput // 确定性 PRNG（mulberry32） export function mulberry32(seed: number): () => number

3.3 daily-settler 模块详细

每日结算编排器——全世界并行 sim。

// 每日 10:00 结算流程 async function dailySettle(day: number) { const worlds = await getActiveWorlds(); // 按世界分片，并行入队 const jobs = worlds.map(w => ({ name: `settle-world-${w.id}`, data: { worldId: w.id, day }, })); // BullMQ 队列，worker 按世界并行消费 await settleQueue.addBulk(jobs); } // 单世界结算 worker async function settleWorld(job) { const { worldId, day } = job.data; const matchups = await getTodayMatchups(worldId, day); for (const m of matchups) { const input = await buildSimInput(m); const output = simulate(input); // 纯函数 await saveResult(m, output); await publishPbp(m, output); // SSE 推送 } await applyPostMatch(worldId, day); // 疲劳/状态/成长 }

5.2 分片策略

  • 按 world_id 分区：players/teams/matches 等大表按 world_id 分区，避免单表热点。
  • 读写分离：写主库，读副本（Dashboard/查询走副本）。
  • 冷热分离：历史赛季数据（>2 季前）归档到冷存储，主库只留近 2 季。

6.1 全球时钟

对齐世界与联赛结构 §6 的全球时钟节点：

时间(UTC+8)事件技术实现

6.2 结算时序

Cron 10:00 → 加载全世界 → 按世界入队 → Worker 并行 sim → 保存结果 → SSE 推送 PBP → 16:00 翻天

6.3 sim seed 生成

// 确定性 seed = hash(worldId, season, day, matchSeq) // 保证同一比赛可重放——审计/回放/防作弊 function genSimSeed(worldId, season, day, matchSeq): number { return hash(`${worldId}:${season}:${day}:${matchSeq}`); }

6.4 结算窗口性能预算

指标预算
单场 sim 耗时≤200ms（纯函数，无 IO）
单世界每日比赛~8 场（16 队/组 ÷ 2）
10 个世界并行~80 场 × 200ms = 16s（单 worker）
4 worker 并行~4s 完成全部 sim
SSE 推送延迟sim 完成后 ≤1s 开始推送
结算总窗口10:00-10:05（5 分钟内完成）

8确定性与重放

核心机制：sim-engine 是纯函数，seed 确定性保证——同一 SimInput 永远产出同一 SimOutput。这是可单测、可回放、可灰度调参、可防作弊的基础。

8.1 确定性保证

  • PRNG：mulberry32，种子由 genSimSeed(worldId, season, day, matchSeq) 生成。
  • RNG 消耗顺序：严格固定——同一 sim 路径中 RNG 调用顺序不变。
  • 无副作用：simulate() 不读写 DB/不调网络/不依赖时间戳。
  • 浮点谨慎：避免不同平台浮点差异（尽量用整数运算或固定精度）。

8.2 回放

  • 每场比赛的 SimInput + sim_seed 存档。
  • 回放 = 重新调用 simulate(savedInput)，输出与原始一致。
  • 回放用于：观赛回放、争议仲裁、bug 复现、平衡性调参验证。

8.3 灰度调参

// 灰度参数存储在 Redis，sim 时注入 async function buildSimInput(matchup): SimInput { const config = await redis.get("sim-config:live"); // config 可热更新——不需重启服务即可调参 // 调参后下一场 sim 立即生效；旧比赛不受影响（seed+input 不变） return { matchup, seed: genSimSeed(...), config, ... }; }

8.4 防作弊审计

  • RNG 日志：每场 sim 记录 RNG 消耗日志（rngLog），可审计是否被篡改。
  • 结果校验：任何争议可重放 sim 验证结果一致性。
  • 服务端权威：前端永不执行 sim——比赛结果只能来自服务端。

10性能与扩展

10.1 性能瓶颈分析

场景瓶颈对策

10.2 扩展策略

  • 世界级隔离：每个世界独立分片，互不影响。世界数增长 = 加 worker。
  • sim worker 无状态：worker 可随时增减，按队列消费。
  • 读副本：查询走副本，结算写主库。
  • 缓存层：Dashboard/排名/统计走 Redis 缓存。

11安全与反作弊

11.1 服务端权威

  • 所有 sim/经济/成长计算在服务端；前端只读结果。
  • 前端任何输入（阵容/战术/训练/交易）经服务端校验后生效。
  • 09:30 提交截止由服务端 Redis 锁强制——前端时间不可信。

11.2 确定性审计

  • 每场比赛存 SimInput + seed + rngLog。
  • 争议可重放验证——结果不一致=服务端 bug（非玩家作弊）。
  • 玩家无法影响 sim——seed 由服务端生成，输入由服务端组装。

11.3 反多账号

  • 同设备/同 IP 多账号检测。
  • 同世界多账号禁止——防自我交易套利。
  • 交易模式检测——反复单向交易触发审查（社交系统 §12）。

11.4 商业化隔离

  • Credits 与薪资空间完全隔离（商业化系统 §10）——代码层防火墙。
  • 付费操作全审计——可追溯是否有红线违规。

11.5 认证与授权

  • JWT 认证；Redis 会话管理。
  • 按角色/世界隔离——A 世界经理不能操作 B 世界数据。
  • 敏感操作（交易/签约/充值）二次确认。

12CI/CD 与开发环境

12.1 代码仓库结构

── Monorepo（pnpm workspace） ── hwo/ ├── packages/ │ ├── shared/ # 共享类型与纯函数（sim-engine 核心在此） │ │ ├── types/ # Player/Team/Matchup/SimInput 等 │ │ ├── sim/ # simulate() 纯函数 + mulberry32 │ │ └── prng/ # 确定性 PRNG │ ├── api/ # NestJS 服务端 │ ├── web/ # React + Vite 前端 │ └── worker/ # BullMQ sim worker ├── docker-compose.yml ├── pnpm-workspace.yaml └── .github/workflows/

12.2 CI 流水线（GitHub Actions）

Push → Lint + Type Check → Unit Test → sim 确定性测试 → Build → Deploy staging

12.3 sim 确定性测试

  • CI 中跑确定性测试——固定 seed 跑 sim，断言输出与快照一致。
  • 若 sim 逻辑变更导致输出变化，测试失败——强制开发者确认是有意变更。
  • 这保证 sim 不会被意外破坏（如浮点优化/重构引入非确定性）。

12.4 开发命令

# 起全套开发环境 docker compose up -d # 前端开发（HMR） pnpm --filter web dev # 后端开发（热重载） pnpm --filter api start:dev # 跑 sim 单测 pnpm --filter shared test # 跑确定性测试 pnpm --filter shared test:determinism

14MVP 技术范围

MVP 原则：17 个系统不可能同时进 MVP。MVP 只做核心循环——让玩家能"组建球队→设战术→每日比赛→看结果→调整"的最小可玩闭环。其余系统分期迭代。

14.1 MVP 范围（M1 里程碑）

系统MVP 状态说明
Sim Engine✅ 核心完整——纯函数 PBP 生成
战术系统✅ 核心基础战术（L1）+ 预设库；规则 DSL 可延后
世界与联赛✅ 核心单世界 + T1-T4 金字塔 + 全球时钟结算
签约转会✅ 核心自由市场签约 + 基础交易；续约/裁员可延后
训练系统简化基础训练计划 + 负荷；专项/恢复可延后
球员成长简化成人阶段成长；童子/少年可延后
AI 经理✅ 核心填充 AI 球队基础决策
球探系统延后MVP 用全可见（无 fog）简化
选秀系统延后MVP 用自由市场替代
三身份系统延后MVP 仅经理身份
关系系统延后MVP 无
王朝传承延后MVP 无（需多赛季才显效）
财务球馆简化基础收入/薪资空间；球馆升级可延后

14.2 MVP 核心循环

组建球队（自由市场签约） → 设阵容+战术（L1 基础） → 提交（09:30 前） → 每日 10:00 sim 结算 → 观赛（SSE PBP） → 看 Box Score → 调整→下一日
